1. Программная инженерия

Программная инженерия (Software Engineering) — это область науки и практики, которая занимается разработкой, внедрением и сопровождением программного обеспечения с применением инженерных подходов.

Главная цель — создавать ПО, которое:

  • работает и решает поставленные задачи;
  • надёжно — не падает и не теряет данные;
  • сопровождаемо — легко изменять и дорабатывать;
  • экономически выгодно — укладывается в сроки и бюджет.

Чем программирование отличается от программной инженерии

Программирование Программная инженерия
Написание кода Весь жизненный цикл ПО
Один разработчик Команда специалистов
Задача — «чтобы работало» Задача — «чтобы работало надёжно и долго»
Фокус на синтаксисе Фокус на процессах, качестве, управлении
Личный результат Продукт для пользователей

Программирование — это часть программной инженерии, но не вся она.

Ключевые области программной инженерии

Область Что изучает
Управление требованиями Сбор, анализ, документирование требований
Проектирование Архитектура, шаблоны, UML
Разработка Написание кода, стиль, рефакторинг
Тестирование Виды, методы, автоматизация
Сопровождение Поддержка, обновления, исправления
Управление проектами Сроки, бюджет, риски, команда
Управление качеством Метрики, стандарты, аудит
Конфигурационное управление Версионирование, сборка, релизы

2. Современные принципы разработки ПО

Основные принципы

Принцип Что означает
Модульность Система разбита на независимые модули
Абстракция Скрытие деталей реализации
Инкапсуляция Данные и методы объединены в одном месте
Иерархия Система имеет уровни (слои)
Повторное использование Компоненты применяются многократно
Слабая связанность (loose coupling) Модули мало зависят друг от друга
Высокая связность (high cohesion) Модуль делает одну задачу хорошо
Расширяемость Легко добавить новое без переделок
Тестируемость Код легко проверить автотестами

Принципы SOLID

Принцип Расшифровка Суть
S — Single Responsibility Единственная ответственность Один класс — одна задача
O — Open/Closed Открыт/закрыт Открыт для расширения, закрыт для изменения
L — Liskov Substitution Подстановка Барбары Лисков Наследник заменяет родителя без ошибок
I — Interface Segregation Разделение интерфейсов Много маленьких интерфейсов лучше одного большого
D — Dependency Inversion Инверсия зависимостей Зависимость от абстракций, а не от реализаций

Другие принципы

Принцип Что означает
DRY (Don't Repeat Yourself) Не повторяйся — избегай дублирования
KISS (Keep It Simple, Stupid) Делай проще
YAGNI (You Aren't Gonna Need It) Не делай того, что не нужно сейчас
Boy Scout Rule Оставляй код чище, чем был
Fail Fast Ошибка должна проявляться сразу
Separation of Concerns Разделение ответственности между модулями

3. Методы разработки программных приложений

Классические методы

Метод Суть
Waterfall (каскадный) Последовательное выполнение этапов
V-модель Каскад + тестирование на каждом уровне
Инкрементный Продукт растёт частями
Итеративный Повторяющиеся циклы улучшения
Спиральный Витки с анализом рисков

Гибкие методы (Agile)

Метод Суть
Scrum Спринты, роли, артефакты
Kanban Визуализация потока задач
XP (Extreme Programming) Парное программирование, TDD
Lean Устранение потерь
FDD (Feature-Driven Development) Разработка по функциям
DSDM Динамическая разработка систем

DevOps и CI/CD

Понятие Что означает
DevOps Объединение разработки и эксплуатации
CI (Continuous Integration) Непрерывная интеграция кода
CD (Continuous Delivery) Непрерывная доставка
CD (Continuous Deployment) Непрерывное развёртывание

Методы тестирования

Метод Что проверяет
TDD (Test-Driven Development) Сначала тест, потом код
BDD (Behavior-Driven Development) Поведение системы
ATDD (Acceptance TDD) Приёмочные тесты
Модульное Отдельные функции
Интеграционное Взаимодействие модулей
Системное Система целиком
Регрессионное Что старое не сломалось

4. Организация работы в команде разработчиков

Роли в команде

Роль Что делает
Product Owner Владелец продукта, приоритеты
Scrum Master Помогает команде, устраняет препятствия
Team Lead Технический лидер
Архитектор Проектирует архитектуру
Аналитик Собирает требования
Разработчик Пишет код
Тестировщик (QA) Проверяет качество
DevOps Автоматизация, развёртывание
Дизайнер Проектирует интерфейс

Методологии командной работы

Методология Особенности
Scrum Спринты (2–4 недели), ежедневные митинги, ретроспективы
Kanban Визуальная доска, ограничение WIP
XP Парное программирование, TDD, частая интеграция
Waterfall Последовательные этапы, формальные роли

Практики командной работы

Практика Что даёт
Daily Standup 15-минутный митинг: что сделал, что буду, что мешает
Code Review Проверка кода коллегами
Pair Programming Два разработчика за одним компьютером
Retrospective Разбор итогов спринта
Planning Poker Оценка задач командой
Sprint Review Демонстрация результата заказчику
Backlog Refinement Уточнение задач

Инструменты командной работы

Инструмент Для чего
Git / GitHub / GitLab Контроль версий
Jira / Trello / Asana Управление задачами
Slack / Teams / Discord Коммуникация
Confluence / Notion Документация
Jenkins / GitHub Actions CI/CD
Figma Дизайн
Miro Мозговые штурмы

Схема Scrum-процесса

Product Backlog -> Sprint Planning -> Sprint Backlog -> Sprint (2-4 недели)
    |
    v
Daily Standup (каждый день) - работа над задачами
    |
    v
Sprint Review -> Increment -> Retrospective
    |
    v
Следующий спринт
